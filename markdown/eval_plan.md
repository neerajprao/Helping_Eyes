**Decisions at Checkpoint 0**

1. The expiry bug is **fixed before the evaluation** (`_EXPIRY_LABEL` and the month-name branch in `assistant.py`,
   with the regression test `test_expiry_dates_are_found_in_common_label_wordings`). The evaluation measures the fixed
   app, and each result file records the git commit and whether the tree was dirty.
2. QA runs at **both temperatures**: 0 (reproducible) and 0.2 (the live app's setting).
3. One Gemini call was made to check the key. It got **HTTP 503 "model is currently experiencing high demand"**, not
   an authentication error, so the key is accepted. Retry rule for every Gemini call: on 503 or 429, retry up to 3
   times with a 30 s pause. Every retry is logged, and a call that still fails counts as a **service error**,
   reported separately and not scored as a wrong answer.
4. Evaluation date: **2026-10-19**.
5. The existing `.venv` (Python 3.13.9) is kept.
6. Tesseract: `--oem 1 --psm 3` primary, `--psm 6` secondary.
7. Section 2.2 (preprocessed conditions): explained again in plain words at Checkpoint 1; still open.

The evaluation measures three things:

1. **OCR accuracy on real photos:** Apple Vision vs RapidOCR vs Tesseract, with and without the app's preprocessing.
2. **Answer accuracy:** Gemini Flash-Lite vs Qwen 2.5 3B, including correct "not on the label" replies.
3. **Speed:** the performance table measured again, now with Apple Vision.

Ground rules: every number comes from a script in `eval/`. Raw per-item results are saved as JSON in `eval/results/`.
`markdown/eval_results.md` is generated by `eval/make_results.py`, never typed by hand. Bad results are reported as they are.

**Two consequences for the plan:**

- In normal (capture) mode the app **never dewarps or deskews**; those steps run only on the book path. "Preprocessed,
  exactly as the app does it" therefore means a different pipeline per category (section 2.2).
- **Bug found in Phase 0 (fixed after Checkpoint 0, see decision 1):** `expiry_dates()` finds nothing in `Exp. Date 02/2027` or `Exp.Date:02/2027`.
  The month-name branch matches "Dat"+"e", the month lookup fails, and the match is dropped without the numeric
  branch being tried. `EXP DATE 02/2027`, `Exp. 02/2027` and `Expiry Date: 02/2027` work. `Exp Dt. 02/27` also fails.
  With Qwen in the Phase 0 timing test this gave the contradictory answer "The text does not show an expiry date. It
  is valid until February 2027."

## 1. Dataset (Phase 1)

- **Size:** 40–50 photos, taken by you. Categories: `medicine_strip`, `medicine_box`, `food_label`, `book_page`,
  `document`, `sign_or_screen`; about 7–9 per category. At least 10 deliberately difficult (dim, glare, curved,
  tilted, small print). Mostly phone, some laptop webcam (through the app's own capture).
- **Manifest:** `eval/data/manifest.csv` with `id, category, lighting (good/dim/glare), angle (flat/tilted/curved),
  device (laptop webcam/phone), notes`. It holds only these fields, so it can be committed.
- **Privacy:** no names on prescriptions, no addresses, no faces, no phone numbers. Raw photos and the full typed
  text stay in the git-ignored `eval/data/private/`. Only metrics and per-item scores are committed, unless you say a
  specific item can be published.
- **Expiry mix:** 2–3 items whose expiry date is already past (old medicine or food), so "is it expired?" has both
  answers in the set.

## 2. OCR accuracy (Phase 3)

### 2.1 Ground truth (Phase 2)
You draw **one box** per photo around the part to transcribe, on the original photo, and type it line by line
while looking only at the photo. No engine output is shown or used to pre-fill. For labels, the box should hold the
key fields (expiry, batch, dosage, ...). For book pages, 5–8 lines. Key fields are typed separately as well.
Unreadable characters are typed as `[?]`; each one matches any single character at no cost, so all engines are
treated the same. The box is stored normalised (0–1), so it does not depend on image size.

### 2.2 Engines and conditions
Every condition starts from the photo decoded and downscaled exactly as `/api/capture` does (`_decode`, 1600 px).

| Engine | Setting (fixed in advance, not tuned on the data) |
|---|---|
| Apple Vision, accurate | the app's setting: `recognize_text()` |
| Apple Vision, fast | `recognize_text(fast=True)`; quick, so it is included |
| RapidOCR 3.9.2 | `RapidOCR()` defaults, as the app used it before commit `1759476` |
| Tesseract 5.5.1 | `--oem 1 --psm 3 -l eng` (LSTM, automatic layout) as primary; `--psm 6` reported as a secondary sensitivity check |

| Condition | What each engine reads |
|---|---|
| **raw** | the decoded photo cropped to your box (plus a 2 % margin) |
| **preprocessed** | the app's own pipeline run on the **full** photo (it needs the page outline to flatten): the **book path** (`read_page(enhance=True)`: flatten, spine split, deskew, dewarp, tone) for `book_page`, the **capture path** (`read_text_enhanced()`: original / flattened / tone / binarised, best by Vision's confidence) for every other category. The transforms the app chose are then applied to your box (homography, crop, rotation, dewarp shift), and that region of the preprocessed image is what every engine reads |
| **app end-to-end** (Vision only) | the app's real output for the whole photo, keeping only the lines whose centre maps back inside your box. This is the text the live app would hand to the language model |

The candidate the capture path picks is chosen with Apple Vision's confidence, as in the app. For RapidOCR and
Tesseract, "preprocessed" therefore means "the image the app's pipeline prepared". A check makes sure my wrapper
returns exactly the same text as `read_text_enhanced()` / `read_page()` for every item, so it cannot quietly differ
from the app.

### 2.3 Metrics
- **Normalisation (documented in `eval/common.py`):** Unicode NFKC; curly quotes → straight quotes; en/em dashes →
  `-`; all whitespace runs, including line breaks, → one space; trimmed. **No lowercasing**, no punctuation removal.
- **CER** = character Levenshtein distance / reference characters. **WER** = the same on words. Main figure: corpus
  level (total edits / total reference length); per-item median also reported. Library: `rapidfuzz` (pinned).
- **Field accuracy:** each typed key field is checked against the engine's output. Dates are parsed with the app's
  own grammar (`assistant.expiry_dates` for expiry; the same date patterns for manufacture date) and compared as
  dates. Other fields (batch, dosage, product name, price, page number, chapter title) count as correct when the
  value, with whitespace removed and case folded, appears in the output normalised the same way. This rule is stated
  in eval_results.md because it is more lenient than CER.
- **Failure rate:** share of items where the engine returns no text in the region.
- **Time per image** for each engine and condition (the preprocessing time is listed separately).
- **CIs:** 95 % percentile bootstrap, 10,000 resamples over **photos**, fixed seed. Differences (preprocessed − raw,
  engine A − engine B) use a **paired** bootstrap. Every table states *n*.
- **Breakdowns:** per category (*n* ≈ 7–9 each, so the CIs will be wide, and eval_results.md says so); the difficult subset
  (lighting ∈ {dim, glare} or angle = curved) on its own.
- **Error analysis:** the 10 worst items (Apple Vision, app end-to-end) with what went wrong (missed line, wrong
  order, character confusions, language correction "fixing" a code, crop cut-off). In committed files the excerpts
  are shown only for items you mark as publishable; the others show the error type only.
- Output: `eval/results/ocr_items.json` (per item × engine × condition), `eval/results/ocr_summary.json`.

## 3. Answer accuracy (Phase 4)

- **Questions:** at least 50 (target 55–60) in `eval/data/questions.json`, drafted by me from **your typed labels
  only** and reviewed and corrected by you before anything runs (Checkpoint 4a). Mix: expiry date and "is it
  expired?", dosage, ingredients or warnings, product name or price, page number or chapter title, and **at least 12
  "not on the label"** questions (things a user would ask that the label does not say).
- **Fixed evaluation date:** `2026-10-19` (question 4). It is set by replacing `assistant.date` with a subclass whose
  `today()` returns that date, for the eval process only. No app code changes; the prompts, the date checks and the
  verdict note are produced by the app's own code.
- **Path:** a fresh `DocAssistant` per question, `set_document(text)` (book pages also get the page facts and label
  that `read_page` produced), `set_provider(...)`, then `ask(question)`, exactly as `/api/ask` does after `classify()`.
- **Text sources × models:** {true text (your typed region), Apple Vision raw, Apple Vision app end-to-end} ×
  {Gemini `gemini-3.1-flash-lite`, Qwen `qwen2.5:3b-instruct`} = 6 runs per question.
- **Temperature:** both 0 and 0.2 (the app's own value). The harness changes only the `temperature` field of the
  outgoing request; everything else is the app's request. That gives 12 runs per question (3 sources × 2 models × 2
  temperatures). Headline numbers use 0.2, because that is what the live app does; 0 is reported next to them.
- **Scoring:**
  - Rules first: normalised exact match for dates, numbers, prices, batch and page numbers; expiry verdict = the
    answer says expired / not expired, matched against the gold verdict on the fixed date.
  - "Not on the label" = the app's own `last_not_in_text` flag (tag or backup regex), plus a rule check of the
    answer's wording.
  - Free-text answers (warnings, ingredients, dosage wording) by a **judge model different from both models under
    test**. You choose it at Phase 4 (options: `qwen2.5:7b-instruct`, local and free but the same family as Qwen 3B;
    or a different Gemini model such as Gemini 2.5 Flash, but the same vendor as the Gemini under test). It is
    reported as an automated judgement, and you spot-check 20 judged items.
- **Metrics (95 % CIs, bootstrap over photos because questions about one photo are not independent):** answer
  accuracy; correct "not on the label" rate (on the ≥12 absent questions); false "not on the label" rate (it said
  absent although the answer was there); hallucination rate (it stated a specific fact not in the given text: rule
  check that every number or date in the answer appears in the source text, plus the judge for free text); expiry
  verdict accuracy, reported separately for the code verdict (`expiry_checks`) and for the spoken answer; time to
  first token (first streamed chunk) and to first sentence, and total answer time.
- Output: `eval/results/qa_items.json`, `eval/results/qa_summary.json`, `eval/results/qa_judge_spotcheck.json`.

## 4. Speed (Phase 5)

The real app (`uvicorn server:app`) on this Mac, localhost, at least 20 timed runs per operation after 1 warm-up
that is excluded; p50 and p95 (plus mean and min/max) are reported. Inputs are made the way `app.js` makes them.

| Operation | How |
|---|---|
| Live frame round trip, a label and a dense two-page spread | WebSocket client → `/ws/live` with a 960 px JPEG at quality 0.7 (as `app.js:435`), time from send to reply. This is client → server → client over localhost; the browser's own canvas/JPEG step is not included, and eval_results.md says so |
| Capture request | `POST /api/capture`, 1920 px JPEG at quality 0.92 (`app.js:490`) |
| Book page request (with word boxes) | `POST /api/book/page`, 1600 px JPEG at quality 0.9 (`app.js:701`); the model paragraph step runs as in the app, so it is measured with and without a model |
| Preprocessing alone, OCR alone | in-process: `capture_candidates()` / `read_page` transforms vs `recognize_text()` on the same photos |
| Language model, TTFT and total | `DocAssistant.ask()` for Gemini and Qwen 3B, 20 questions each |
| Kokoro, time to first audio | `commands.synthesize()` on a typical answer sentence, after warm-up (`TTS_ENGINE=kokoro`) |
| End to end, question to first spoken word | `POST /api/ask` → first `sentence` event → `POST /api/tts` → audio bytes received. Browser speech recognition and audio start are not included |

The machine, OS, Python and package versions, model names, git commit and settings are recorded in
`eval/results/latency.json`.

Only text is ever sent, never photos. Calls are spaced **at least 4.5 s apart** (≤ 13 per minute).

| Use | Calls |
|---|---|
| Key check (done: 1 call, HTTP 503) | 1 |

| Speed: 21 TTFT runs + 21 end-to-end runs | ~42 |
| Judge, only if a Gemini judge is chosen: ~15 free-text questions × 3 sources × 2 models × 2 temperatures | ~180 |
| Retries after 503 / 429 | unknown, logged |

## Risks and limits (they go into eval_results.md)

- **Small, author-collected dataset** (40–50 photos, one person, one home): CIs will be wide, per-category ones very
  wide. It is not a benchmark and cannot be compared with published OCR benchmarks.
- **One device per class** (one phone, one Mac webcam), one Mac for timing.
- **Labels are typed by the author**, once; there is no second labeller, so label errors are not measured. The
  consistency check (Phase 2) catches only mechanical mistakes.
- **Region choice:** you choose the region, which could favour text that is easy to read. The shot list and the
  rule "box the key fields, not the clearest lines" reduce this.
- **Engine fairness:** RapidOCR's default model is the Chinese+English PP-OCR model (how the app used it); Tesseract
  is not tuned per image. Apple Vision's language correction can "correct" codes such as batch numbers; this shows
  in field accuracy and the error analysis.
- **Preprocessing is chosen with Vision's confidence**, so on the capture path it is tuned to Vision; this is
  stated next to the RapidOCR and Tesseract "preprocessed" numbers.
- **Automated judge** for free-text answers; spot-checked on 20 items, but still an automated judgement.
- **Gemini is a hosted model** that can change without notice; the model name and run date are recorded. Temperature
  0 still does not make it fully deterministic.
- **Speed** is measured on localhost, without the browser's encode, network or audio-start time.
- **The expiry bug** above affects the expiry results unless it is fixed first.
